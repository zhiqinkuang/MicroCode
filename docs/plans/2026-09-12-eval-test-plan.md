# Coding Agent 效果评测（Eval）测试计划

**分支**：`agent_eval`（从 `main@f45355d` 拉出）
**日期**：2026-09-12
**状态**：待评审。**本文件不含任何完成率承诺**——所有百分比都是待检验的假设。

## 0. 一句话目标

用**可复现**的实验回答一个问题：**Skill 按需加载、SubAgent 上下文隔离、分级权限与安全审查这三个机制，
在复杂编码任务上分别带来多少收益、多少代价？**

不是「证明它们有效」，是「测出它们各自值多少」。测出来是负的也照实报。

## 1. 待检验的假设（H 系列）

| 编号 | 假设 | 主要观测 | 反面可能 |
|---|---|---|---|
| H1 | SubAgent 上下文隔离降低总 token | 总 token（含子代理） | 隔离要求把背景完整交代，短任务反而更贵 |
| H2 | Skill 按需加载降低总 token 且不降完成率 | 总 token + 完成率 | 省了 token 但漏用了 skill 导致完成率下降 |
| H3 | 分级权限与安全审查不显著损害完成率 | 完成率 + 需人工审批次数 | 审批打断流程，完成率下降 |
| H4 | 三者叠加优于任一单独使用 | 完成率（V3 vs V1/V2/V0） | 叠加后互相干扰 |
| H5 | 闭环闸门提升完成率但推高 token | 完成率 + 拦停次数 + token | 闸门只是空转，完成率不变 |

**H5 单独列出来**是因为它最容易读错：闸门会在模型改过文件却没验证时拦停最多 3 次，
所以「开闸门」的版本天然多花 token、多跑轮次。不把拦停次数一起报，读者会把闸门的代价误判成模型变差。

## 2. 先决条件：P0 计量修复（不修则全部数字无效）

### 2.1 已确认的缺陷

```
main.py:108-110   state.input_tokens += usage.input_tokens     ← 只累加主 agent 的 result.usage
subagents.py      全文 grep usage → 只有 UsageLimits（限额），无任何用量回传
```

子代理在 `run_subagent` 里独立跑，**它的 token 不计入任何计数器、也不写进会话**。
影响：任何用过 `run_agent` 的场景，token 数字**必然偏低**；而子代理是 token 大户
（全新上下文需完整交代背景 + 最多 40 轮 + 最终报告）。因此「Token 降低 N%」在修复前**不可信**，
可能是「省掉的部分没被计」而非真的节省。

### 2.2 修复方案

1. `run_subagent` 结束时取 `run.result.usage`，写入 job（新增字段 `job.usage`）。
2. 主循环结算时把已完成 job 的用量并入 `state.input_tokens/output_tokens`；
   同一 job 只并入一次（用 `job.notified` 不行——那是通知语义；新增 `usage_settled` 标志）。
3. 同时把闭环拦停次数（`IterationState.interventions`）与 subagent 调用次数写进结果元数据。
4. 离线回归测试：假模型驱动一次派发，断言子代理用量出现在会话累计里，且不重复计入。

### 2.3 验收判据

- 一个「主 agent 派发 1 个子代理」的离线场景，会话累计 token **严格大于**主 agent 单独的 token。
- 重复结算不重复计入（跑两次结算，总量不变）。
- `/status` 展示的口径与实际一致。

## 3. 指标口径（先写死，避免事后各说各话）

| 指标 | 定义 | 采集点 |
|---|---|---|
| **完成率**（主指标） | 目标仓库的指定测试由 **fail → pass**，且判定器未标记作弊 | 判定器（见 §5） |
| 总 token | 主 agent + 全部子代理的 input+output 之和 | P0 修复后 |
| 主 agent 轮数 | 一次任务内主 agent 的 model 调用次数 | `api_call_log` |
| 子代理调用次数 | `run_agent` 成功派发数 | job 注册表 |
| 闸门拦停次数 | `IterationState.interventions` 累计 | 结果元数据 |
| 需人工审批次数 | 走到 `prompt_approval` 的调用数（判定为「摩擦成本」） | 权限层计数 |
| wall-clock | 任务从开始到结束的秒数 | 运行器 |
| 成本 | 按 token 与单价换算 | 后处理 |

**口径纪律**：这几个定义一旦定下，**实验中途不得更改**。改了要重跑全量并在报告里说明。

## 4. 版本矩阵（消融设计）

同一个 Agent、同一个模型、同一套工具、同一个 system prompt，**只切机制开关**：

| 版本 | Skill | SubAgent | 权限分级 | 闭环闸门 | 用途 |
|---|---|---|---|---|---|
| **V0 Base** | ✗ | ✗ | ✗（bypass） | ✗ | 基线 |
| **V1** | ✓ | ✗ | ✓ | ✓ | 量出 skill 的增量 |
| **V2** | ✗ | ✓ | ✓ | ✓ | 量出 subagent 隔离的增量 |
| **V3 全量** | ✓ | ✓ | ✓ | ✓ | 量出叠加效果 |

**可选 V4**：V3 但关闸门 → 专门回答 H5。

**基线必须是「同一系统关掉开关」**，而不是别的 Agent 系统。理由：归因干净、可复现；
外部基线需要完整交代其配置，否则「+N pp」没有意义。若日后要引入外部基线，单独立一节说明。

**开关的实现方式**（不改产品行为，只加实验用入口）：

- Skill：不调用 `discover_skills` 即等价于无 skill（或用环境变量 `CODING_AGENT_DISABLE_SKILLS=1`）。
- SubAgent：从工具表摘掉 `run_agent`，主 agent 自己做子任务。
- 权限：`permissions.state.mode` 置 `bypass`。
- 闸门：`AgentDeps.iteration = None`（闸门取到 None 即放行，是既有行为）。

## 5. 判定器（Decision Oracle）——本计划最容易被做坏的一环

### 5.1 判据

`PASS` 当且仅当：任务开始前**指定的测试**（不是模型自己挑的）由 fail 变 pass，且未触发作弊检测。

### 5.2 必须检测的作弊模式

| 模式 | 检测方式 |
|---|---|
| 改测试而不是改实现 | 任务夹具里的测试文件在运行前后**哈希必须一致**且模型未写入该路径 |
| 删除 / 跳过失败测试 | 断言测试收集数不减少（pytest 的 `--collect-only` 计数对比） |
| 硬编码用例输出 | 用夹具里的**隐藏用例**（模型看不到）复跑一次 |
| 让测试恒真 | 检测 `assert True` / `pytest.skip` / `xfail` 的注入、`conftest` 被改 |
| 改判定相关配置 | `pytest.ini` / `pyproject.toml` / `conftest.py` 的哈希监控 |

### 5.3 判定器自身的验证（不可跳过）

准备一批**已知答案的运行记录**（人工标注：正确修复 / 作弊 / 未完成），喂给判定器，要求：

- 正确修复 → PASS
- 各类作弊 → 全部判为 FAIL 并给出理由
- 未完成 → FAIL

**判定器误判率必须 < 5%，否则先修判定器再放量。** 一个会把作弊判成通过的判定器，
产出的完成率比没有完成率更有害。

## 6. 场景集

### 6.1 分层

| 层 | 来源 | 规模 | 用途 |
|---|---|---|---|
| **L1 冒烟** | 本仓库 `test/bubble_sort.py` 类自建小任务 | 3-5 | 验证管线本身，不进结论 |
| **L2 自建集** | 我造 + 你审 | 20-30 | 消融实验（只需相对差异，不需外部可比性） |
| **L3 公开基准** | SWE-bench-lite / HumanEval / MBPP 之一 | 按基准规模 | **主结论**，外部可复现、审稿人认 |

**为什么主结论必须挂公开基准**：Agent 的实现者、任务集的作者、判定标准的作者，
这三重身份一旦重叠，「78.8%」就无法回答「这些任务是谁选的、为什么是这些」。
公开基准直接消掉这个弱点。

### 6.2 场景集纪律

- 每个任务：**任务描述 + 起点代码 + 指定测试 + 隐藏用例**，四件套齐全才算一个场景。
- 任务描述里**不得泄露**它属于哪个版本、或评测意图。
- 场景集在实验开始前冻结（哈希记录），中途不增删；若必须改，全量重跑。

## 7. 阶段与闸门（Gate）

每个阶段有**明确的进入下一阶段的条件**，不满足就停在这一步。

### P0 · 计量修复与口径定稿 —— 无 API 成本
**产物**：`agent/iteration.py` 等改动 + 回归测试 + 本文件 §3 口径定稿
**闸门 G0**：§2.3 三条验收判据全过；`ruff` / 全量 pytest 全绿。

### P1 · 单任务运行器 + 判定器 —— 少量 API 成本
**产物**：`scripts/eval/run_task.py`（跑一个任务产出结构化 JSON）、`scripts/eval/judge.py`、判定器自测
**闸门 G1**：
1. 判定器自测通过（§5.3，误判率 < 5%）；
2. 同一条运行记录重复判定结果一致（判定器确定性）；
3. token 口径与 P0 修复一致（手工核对一次运行的主 + 子代理用量）。

### P2 · 试跑管线 —— 20 次真实执行
```
5 个 L1 任务 × 2 版本（V0 / V3）× 2 次重复 = 20 次
```
**目的不是结论，是验证管线**：判定器是否可信、口径是否对得上、单任务耗时与花费。
**闸门 G2**：20 次全部产出结构化记录且无人工干预；据此给出放量成本的**实测**推算
（而不是估算）。**达不到就回到 P1，不要放量。**

### P3 · 放量消融 —— 成本最高，需你明确批准
```
L2 自建集（20-30）× V0/V1/V2/V3 × N 次重复
```
**闸门 G3**：每个格子都是分布（均值 + 方差），不是单次数字；随机性导致的差异与机制差异可区分。

### P4 · 公开基准主结论 —— 需你明确批准
**闸门 G4**：固定 seed / prompt / 模型版本；**原始运行记录全部随产物提交**；
一条命令重跑全量。**没有这一层，数字不可引用。**

## 8. 成本模型（放量前必须实测校准）

```
总执行次数 = 场景数 × 版本数 × 重复次数
P2 试跑    = 5 × 2 × 2  =  20
P3 消融    = 25 × 4 × 3 = 300
P4 公开集  = 基准规模 × 2 版本 × 3
```

**P2 的核心产出之一就是把这个模型从「估算」变成「实测」**：记录单任务平均 token 与 wall-clock，
再推算 P3/P4 的总量与花费，由你决定是否启动。

## 9. 风险与对策

| 风险 | 后果 | 对策 |
|---|---|---|
| Token 漏算子代理（**已确认存在**） | 所有 token 结论错误 | P0 必修，G0 卡住 |
| 判定器把作弊判成通过 | 完成率虚高，比没有更糟 | §5.2 五类作弊检测 + §5.3 判定器自测 |
| 模型随机性被当成机制差异 | 结论方向性错误 | 每格 N 次取分布；报方差 |
| 闭门造场景集导致结论不可外推 | 数字不可引用 | 主结论挂公开基准 |
| 闸门代价被误读为模型变差 | H5 结论反向 | 必报拦停次数 |
| 任务夹具环境不干净（残留文件/缓存） | 假 PASS | 每次运行用干净副本 + 运行前后哈希校验 |
| 单任务跑飞 | 拖垮整体 | 复用 `MAX_SUBAGENT_REQUESTS` 思路做任务级超时与轮数上限 |
| 我既实现 Agent 又造任务集 | 结论可信度受质疑 | 任务集请你审；主结论用外部基准 |

  进 CI 的只有判定器自测与口径回归（离线）。
